# Eval set: the bank baseline (a mostly compliant bank with planted exceptions)

The demo bank used to be tiny (6 branches, 161 loans, two circulars' worth of data). It is now a realistic, fictional, **mostly
RBI-compliant** bank, so that a new circular can be tested against a real position: what is already compliant, what gaps
appear, what is upcoming, and what is only a readiness gap. Everything is generated by `python scripts/generate_synthetic_bank.py`
(seed 2026, reference date 17 Oct 2026) and is byte-for-byte reproducible.

The primary corpus is the RBI Expected Credit Loss timeline (`docs/evals/ecl-timeline.md`, `data/circulars/rbi_ecl_*.md`).
The bank follows the **incurred-loss IRACP Directions** now in force (RBI/DOR/2025-26/164, as updated 1 Jul 2026), has a few
documented exceptions, and has none of the data or controls the final **ACPIR (ECL) Directions** (effective 1 Apr 2027) need.

## 4. Internal policies and controls

- `data/bank/policies.json`: 13 internal policies (Credit, Asset Classification and Provisioning, Fair Practices Code, Rate Reset and Disclosure,
  Collateral and Document Custody, Customer Grievance, KYC and AML, Model Risk Management, Recovery and Restructuring, Outsourcing, Data Governance,
  Agricultural and MSME Lending, Internal Audit). Each clause has an id, owner team, effective date, the RBI instrument and paragraph it implements
  (real paragraph numbers from the corpus, checked by a test against the documents) and the controls that enforce it. Clauses for the ECL
  framework exist in the policies as drafts.
- `data/bank/controls.json`: 53 controls (31 implemented, 6 partial, 6 planned, 10 absent) with owner, evidence references, last test date and
  result, the paragraphs they satisfy, and, where data can evidence them, the data check (a rule of the IRACP template, or an explicit expression).
  The seven original rate-reset and document-release controls are kept.
- **The ECL controls are absent or planned**: staging engine (absent), SICR criteria documentation (planned 2026-12-31), PD, LGD and EAD models (absent),
  EIR computation (absent), macro scenarios (planned), model validation (planned), prudential-floor calculator (absent), and seven more. The
  incurred-loss controls (classification, SMA tagging, provisioning, income recognition, MIS) are implemented.
- `data/bank/architecture.json` carries them: Policy nodes (`kind: internal`), Control nodes, `IMPLEMENTS` (internal Policy to regulatory Rule, 26 edges,
  dangling until the circular is ingested), `ENFORCES` (Policy to Control, 46) and `PROVIDES` (Product to Control). Edges are bitemporal: the
  KYC control is provided from 2026-01-01 and the resolution-plan provisioning control from 2026-07-01, so time travel shows the earlier position.
  Planned controls are enforced only from their go-live date; absent controls by nobody.
- `bank_mcp_server/control_library.py` answers "which controls satisfy this instrument and which are not ready on this date": for ACPIR on
  2026-10-17 that is 16 **readiness gaps** (and 6 carried-over controls already ready); on 2027-04-02 the same 16 are **control gaps**.

## 5. `record_assertion`: the declarative per-record check

The old check kinds (`record_flag`, `control_required`, `event_deadline`) could not express "an account more than 90 days past due must be
classified NPA" or "a substandard unsecured account must hold 25 per cent". A fourth kind does:

```json
{"kind": "record_assertion", "view": "vw_asset_quality",
 "where":  "asset_classification = 'SUBSTANDARD' AND secured = false",
 "assert": "provision_held * 100 >= outstanding_balance * 25", "tolerance": 0}
```

`where` selects the rows in scope, `assert` is what each must satisfy, `tolerance` (0 to 1, default 0) is the share of in-scope rows allowed to fail.
The engine returns `in_scope`, `violations`, `by_branch`, `by_product`, exposure and a worklist of opaque references. In JSON the key is `assert`
(`ComplianceCheck.assertion` in Python); extractions cached before this kind existed still load.

Safety rules (`bank_mcp_server/assertions.py`; enforced in the engine and, for extractions, in `ingestion/validator.py`):

1. Allow-list, not deny-list: only `AND OR NOT ( )`, `= <> != > >= < <=`, `IN` over literals, `BETWEEN`, `IS [NOT] NULL`, `+ - * /`, unary minus,
   number, string and boolean literals, unqualified columns, and the one placeholder `:as_of`. Functions, `CAST`, `CASE`, `LIKE`, `||`, `%`, subqueries,
   `SELECT`, other parameters and hex strings are rejected.
2. One expression of at most 800 characters; no `;`, comment markers, backslashes, control characters or quoted identifiers; at most 120 nodes, 16 levels
   and 20 `IN` values; numbers up to 1e12; strings of at most 40 safe characters.
3. The view must be a sanitized view; columns must belong to it and must not be PII or row identifiers (`loan_ref`, `customer_ref`, `loan_id`), so
   an assertion can count rows but never probe one.
4. Division only by a non-zero number literal (no data-dependent division by zero).
5. Operands are type-checked from the typed column catalogue (`days_past_due > 'x'` is an error; an unknown enum value is a warning).
6. The engine re-serialises the validated AST for the dialect, so no user text reaches the database; the analyst connection is read only; at most
   100,000 rows are read and the query is aborted after 5 seconds (SQLite progress handler; Cloud SQL sessions carry `statement_timeout`).
7. NULL in `assert` counts as a violation. Zero rows in scope is `NOT_EVALUATED`, never `COMPLIANT`.

`tests/test_record_assertion.py` covers about 100 rejected expressions (stacked statements, comments, subqueries, `UNION`, functions, casts,
hex and unicode tricks, other parameters, PII and identifier columns, other views and tables) and cross-checks the engine counts of every IRACP
check against an unguarded query.

Run it:

```bash
python scripts/run_eval_suite.py                 # deterministic pipeline, prints the scorecard, exits 1 on any failed assertion
python scripts/run_eval_suite.py --only iracp    # cases whose id contains the text
python scripts/run_eval_suite.py --list
python scripts/run_eval_suite.py --llm           # Gemini extraction (needs GCP); applies each case's llm_expected; never needed by tests
YUKDHIS_RUNTIME_DIR=$(mktemp -d) venv/bin/python -m pytest -q tests/test_eval_suite.py
```

Scorecard at the time of writing: `28/28 cases passed, 214/214 assertions passed`.

Known gaps these cases record (not asserted as defects):

- No `amendment` or `repeal` document type: the repeal Directions classify as `master_direction` (0.62), the 2026 amendment as `circular` (0.64),
  the 2025 amendment as `master_direction` (0.56).
- ACPIR, the 2025 amendment and the repeal have no template; without an LLM their runs are blocked. Readiness for ACPIR comes from the control
  library, not from rule extraction.
- The data is one snapshot (17 Oct 2026). `as_of` moves effective dates (UPCOMING) and `:as_of` expressions, but a run dated earlier still reads
  the same snapshot.
- Standard-asset provisioning is checked per account; the Directions require it on the global portfolio.
- The extraction prompt (`ingestion/extractor.py`) does not yet describe `record_assertion`, so an LLM extraction cannot produce it until it does.
